# CLAUDE.md — ABIA-Planners

Project: tested distribution of FF 2.3 and Metric-FF 2.1 (Jörg Hoffmann)
plus the ABIA course examples, installable with `pip install abia-planners` on
Windows, Linux and macOS. This is a porting and packaging project, not a
planner-improvement project.

Communicate with the maintainer in Spanish. Code, comments, commit messages and
maintainer documentation in English. Student-facing material in Spanish.

## Standing rules

1. **Semantics are frozen.** Do not change search algorithms, heuristics, default options (Metric-FF 2.1 defaults to `-s 5`: keep it), command-line interface, plan output format or exit codes. Code implementing search, heuristics and instantiation (e.g. `search.c`, `relax.c`, `inst_*.c`) may be modified only to fix a portability or undefined-behaviour problem, with written justification in `PATCHES.md`.
2. **Upstream is traceable.** Import pristine upstream sources verbatim in their own commit and record SHA-256 checksums in `UPSTREAM.md`. Apply every modification as a separate, small commit with a single purpose. List every deviation from upstream in `PATCHES.md`: file, reason, and evidence that output is unchanged.
3. **Acceptance is validity, not identity** (maintainer decision, Checkpoint 1, 2026-11-11). The purpose is educational: on every platform, a build is accepted when, for every case of the test corpus, (a) the outcome class (plan found, proven unsolvable, parse error, usage error, …) and exit code match the golden reference; (b) every plan found is valid for its problem according to the plan validator; (c) the run terminates within the case's time limit without crashing or hanging. Differences in the plan chosen, plan length or search statistics are acceptable. Optimality and bit-for-bit reproducibility are not goals. A case that succeeds on the reference platform but fails, crashes or times out on another is a defect to investigate; if randomness is the cause, report it with evidence.
   **Regression check on the reference platform.** On Linux x86-64 (glibc), the reference build must keep normalised outputs (plans, outcome class, exit code, stdout/stderr; time lines masked) byte-identical to the golden reference after any change to `src/`. This detects accidental semantic changes. For malformed-input cases any change in diagnostic text must be listed in `PATCHES.md`. If a change cannot satisfy this, stop and ask the maintainer.
4. **Fixing undefined behaviour is not free.** If removing UB changes any golden output on the reference platform, stop and report it: the reference behaviour depended on UB and the maintainer must decide.
5. **Capacity limits.** Do not change `MAX_*` constants or other compile-time limits unless a course domain hits them, and only after the maintainer approves. Document any such change.
6. **No substitution.** Never replace FF or Metric-FF with another planner (Ferroplan, Fast Downward, ENHSP, Planutils images, …), not even as a fallback.
7. **Evidence or "unvalidated".** A platform counts as supported only when native CI runners have built it, passed the full corpus and passed a clean-install test. Report everything else as unvalidated.
8. **Licensing.** The distribution is GPL. Keep upstream copyright notices; ship `LICENSE`, `NOTICE` and the corresponding source. Do not copy code from any repository whose licence is missing or incompatible; you may read it as a reference. Flag any licence doubt to the maintainer.
9. **Ask before irreversible or public actions:** creating public repositories, publishing to PyPI or a container registry, creating tags or releases, changing licences, rewriting history.
10. **Randomness.** Both planners call `random()`. Metric-FF 2.1 breaks ties in A*-epsilon (`-s 4`, and `-s 5` when EHC fails) with an unseeded `random() % 2`, and both planners use random values as state-hash keys (in Metric-FF this also affects dominance pruning). FF 2.3 seeds `random()` with the clock's milliseconds: keep that as upstream (its output does not depend on the seed; see `reports/randomness.md`). Windows has no `random()` and C libraries produce different sequences. Provide **one portable, licence-compatible implementation in `src/compat/`** and use it on every platform; by default it reproduces the glibc `random()` sequence, so other platforms can reuse the reference golden outputs. This is a testing convenience, not a correctness requirement (rule 3): output differences caused by randomness are acceptable when the run is valid. Never use the platform's `rand()`.
11. **Course examples are teaching material** (maintainer decision, Checkpoint 1, 2026-11-11). Keep every original as received, for provenance: the source archives/files are stored unmodified with their SHA-256. The shipped copies under `examples/` may be corrected and commented to make them more useful for teaching. Make each such change in its own commit, re-record the affected golden outputs in that commit, and list the change in the example's README. Each example domain lives in its own folder with a short Spanish `README.md`: what it contains, its variants, and a copy-paste command for every problem. Keep author credits where the files carry them. Include all class examples available; never include exams, student work, or third-party binaries/archives (e.g. old `metricff.exe`, `cygwin1.dll`).
